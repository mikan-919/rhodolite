## 1. 結論として動いたもの: 次元は2つではなく、射影が2つ

議論の出発点は「型のレベルで環境が欲しいときと、値のレベルで欲しいときがあり、
その2つは次元が違うから同じ場所に置くと変」だった。

到達したのは**もっと弱い主張で足りる**、というもの。スロットに入っているのは
値ではなく **「型 + その型の実体」の対**。`db(InMemoryDb::new([alice]))` を渡すのは
値の差し替えというより**型の差し替え**で、実体は付随物。

| | 射影 | 綴り | 例 |
|---|---|---|---|
| 値射影 | 対の実体側 | `.` | `db.save(u)` |
| 型射影 | 対の型側 | `::` | `db::new()`（**未実装**） |

ML のモジュールと同じ形（`M.t` が型、`M.f` が値）。1つの束縛に射影が2つあるだけなので、
**宣言形式を2つ用意する必要はない**。

これで落ちる帰結:

- 「値だけ差し替えても意味がない」は正しい。値は必ず型を連れてくる
- 型レベル専用の宣言形式（`@env Database of Database` のような）は不要
- ただし**実体を持たない型**（`effect Str: StringLike = Utf8` を型位置に書く）は
  対にならないので、これだけは別の狭い機能として残る。v2 以降

### 未実装の穴: 型射影が無いので関連関数に届かない

trait の関連関数（`self` を取らないもの）はスロット経由で呼べない。
「提供された Database の実体を1つ作る」が書けない。→ 実測 6

### 追記: 型の提供と実体の提供は別の段階かもしれない

**追記後の議論で決定した。→ [ADR-0005](../adr/0005-with-provision-and-head-blocks.md)**

`db::new()` を考える過程で、「スロットには常に型と実体の対が入る」という上の整理を
再検討する必要が出た。使う側には少なくとも次の2場面がある。

1. 選択された実装型だけが欲しい。`Vec::new()` の `Vec` に相当するものを受け取り、
   初期化は提供先のスコープ内で行いたい
2. 選択された実装型と、すでに初期化された実体の両方が欲しい

現在の `db(Postgres::new(url))` は、次の3操作を一度に行っている。

1. `Database` の実装型として `Postgres` を選ぶ
2. `Postgres` を初期化する
3. 生成した実体を ambient に置く

しかし、初期化に内側の値が必要なら3操作を分けたい。

```rhodolite
db<Postgres>: {                    // 実装型だけを提供
    let connection = db::new(url)  // 内側で初期化

    db(connection): {              // 実体を ambient に提供
        handle()
    }
}
```

この案では `<>` と `()` が型と値に対応する。

| Head | 提供するもの | 使用できる射影 |
|---|---|---|
| `db<Postgres>` | 実装型 | `db::new()` |
| `db(connection)` | 値から分かる実装型 + 実体 | `db::new()` と `db.save()` |

現在の形は、型の選択・初期化・実体の提供を一度に行う短縮形として残せる。

```rhodolite
db(Postgres::new(url)): {
    handle()
}
```

この時点での仮のモデルは、**スロットは名前付きの実装選択であり、必ず選択された
実装型を持ち、段階によっては現在の実体も持つ**、というもの。ただし決定ではない。

実体を常に存在させて遅延初期化する案もあるが、それは単なる表現上の統一ではない。
初回使用時に1回作るか、使用ごとに作るか、初期化引数をどこから得るか、失敗をいつ
報告するか、状態を共有するか、というライフサイクル規則を同時に導入する。そのため
「実体は常にある」とはまだ決めない。

この整理では Jotai との類似も限定される。Jotai に似ているのは、名前付きの値が
Provider の内側へ届き、さらに内側で差し替えられる部分。一方、Rhodolite のスロットは
契約に対する**実装型の選択**を含み、型射影を持ちうる。したがって現時点の比較は、
「スコープ付きの値は Jotai に似るが、スロット全体は Jotai の atom ではない」まで。

未決:

- `db<Postgres>` を型提供の正式な構文にするか
- 型だけ提供された状態と、実体も提供された状態を同じスロットの段階として扱うか
- 外側の `db<Postgres>` と内側の `db(connection)` で、`connection` の具体型一致を
  必須にするか
- `<>` が将来のジェネリック適用と読者・パーサの両方で衝突しないか

## 3. 却下した案とその理由

### `effect Clock`（trait 名をスロット名にする糖衣）

`Clock.now()` と書けるようにする案。**却下。**
`Clock` は trait = 型の世界の住人で、個体になれない（「a Clock」は存在せず、
存在するのは「Clock を実装した何か」）。存在しないものを `.` の左に置くので
読み手のモデルが壊れる。得るものは識別子1個を打たなくて済むことだけ。

そして「Clock を実装した何かが挿さる」は `effect clock: Clock` が**既に実現している**。
糖衣が消していたのは役割名だけで、契約の指定方法は何も変わっていなかった。

役割名は捨てられない側: 呼び出し地点に出る（一番読まれる語）、`primary`/`replica` を
書き分けられる、小文字なので値に見えて違和感が出ない。

### `clock::now()`（スロットの使用を `::` に変える）

**却下。**`::` の第一の客は関連関数で、あれは完全に静的（`Vec::new` は定義に飛べる）。
`now` は `self` を取るメソッド = 値の名前空間なので、`::` にすると
「静的に解決する」約束を破り、**関連関数の側が汚れる**。

規則は Rust と同じで新しくない: `self` を取るなら `.`、取らないなら `::`。
だから `db::new()`（§1 の型射影）は正しく、`clock::now()` は間違い。

### `@Name.method()`（大文字シジル）

**却下 — 一度実装して削除済み。**`7d45ad0`「effect をスロット宣言として導入し、
@ シジルと曖昧性規則を削除」で `@Replica.find(id)` / `@Primary.save(u)` が消えた。
削除理由は「スロットが常に名前を持つので曖昧性が構造的に発生しない」「`@Replica`
シジルと**1つなら省略/2つ以上なら必須**の特例規則が消える」。

**注意**: 消したのはシジルと特例規則の**セット**で、理由は特例規則側にある。
名前衝突は削除理由に入っていない（→ §5 でシジルが再浮上する）。

### 強制の規則（スロット宣言済み trait のメソッドはスロット経由でしか呼べない）

実測 1 の穴を型検査で閉じる案。**単独では却下。**
実測 7 のデコレータが書けなくなる（`self.inner.save(u)` が違反する）。
包む対象を値として握らないとデコレータは作れないので回避不能。
失うのはログ・リトライ・キャッシュ・メトリクス = DI コンテナが使われる理由の大半。

逃げ道はある: **可視性の規則**にする。「スロット経由か、その trait の `impl` の中でのみ」。
`protected` と同じ形。ただし採否は未決（→ §7）。

既定値（§4）を入れると迂回する動機自体が消えるので、**規則を増やさずに同じ効果**が
出る可能性がある。

## 4. 有力だが未決: 既定値

```rhodolite
effect clock: Clock = SystemClock {}
```

提供ブロックなしで `clock.now()` が動き、テストだけが上書きする。
`new Date()` と本番経路のコストが同じになる（現状は `main` に提供ブロックが必要）。

自然に落ちてくる規則が2つ:

1. **既定値は閉じた式でないといけない。** トップレベルにローカル変数が無いので
   `Postgres::new(url)` は書けず `SystemClock {}` は書ける。
   → **設定不要の能力だけが既定値を持てる**という線が自動的に引かれる
2. **既定値を宣言したスロットは提供忘れが起きない。** スロットごとの選択なので、
   `effect db: Database`（提供必須）と共存できる。「既定値を書くか」が
   「提供を必須にするか」の宣言になる

危険: 既定値があるスロットは**テストが黙って本番の能力を使う**。
時計なら軽傷、DB なら事故 — ただし DB は既定値を持てない（規則1）ので構造的にほぼ防がれる。

未決: 既定値をいつ評価するか（毎回 / プログラム開始時に1回 / 初回使用時に1回）。
状態を持つ既定値だと差が出る。

## 5. 名前衝突 — 調査した

### 問い

役割名（`db` `clock` `logger` `cache` `config` `conn` `tx` `store` `rng` `env` `fs`
`http` `queue` `metrics` `session`）は**最頻出のローカル変数名そのもの**。
大きなシステムで干渉しないのか。

### 調査結果: 解決可能。rhodolite は Scala で崩れた側を最初から避けている

Scala 3 が `import x.given` 専用構文を作った理由（公式ドキュメント）:

> givens can be anonymous, so the usual recourse of using named imports is not practical
>
> it is not possible to hide imported givens in a long list of regular wildcard imports

Scala 2 の問題は2要因の積であり、**rhodolite は両方持っていない**:

| 要因 | Scala 2 | rhodolite |
|---|---|---|
| 型で探索する（companion object・package prefix まで） | あり →「どこから来たか分からない」 | 無い。名前で引く。宣言は1箇所 |
| 無名でありうる | あり → 名前で import できない | 無い。スロットは常に名前を持つ |

Koka（エフェクトシステムで最も近い親戚）は同じ結論に外から到達している:
モジュール修飾名で同名関数を区別し、v3.2.3 で「implicit の解決は**一意解を要求し、
スコープを考慮する**」に変更。形式化は PLDI'26 の *Syntactic Implicits with Static
Overloading*（Leijen, Whiting）。
（検索結果では `list/map` / `array/map` という修飾構文が出たが、公式 book のページでは
その構文の詳細を確認できなかった。）

名前付きハンドラは研究の主流方向: *First-class names for effect handlers*（OOPSLA 2022）、
*Rows and Capabilities as Modal Effects with Names*（2025）。
**スロットに名前を強制したのは naive な選択ではない。**

### 分かったこと: 修飾とマーカーは別の問題を解く

| | 解く衝突 |
|---|---|
| モジュール修飾 | 別モジュールが両方 `db` というスロットを宣言している |
| **マーカー** | スロットの `db` と**ローカル変数の `db`** |

**モジュールは後者を解かない。** 修飾されるのは宣言側で、使用側は `db.save(u)` と
裸で書く。使用側を `data/db.save(u)` にしたら言語の存在理由が消える。

そして**動的スコープを裸の名前で綴った実装が存在しない**:

| 実装 | マーカー |
|---|---|
| Clojure | `*dynamic-var*`（earmuffs）+ 名前空間 |
| Common Lisp | `*special*` の慣習 |
| Ruby | `$global` / `@ivar` |
| Racket | パラメータは**呼び出し形** `(current-output-port)` |
| Jotai / React Context | **`useAtom(countAtom)` という呼び出し形** |
| Scala 3 | マーカー無し・無名 → 上記の失敗要因そのもの |

マーカーはシジルでなくてもよい（呼び出し形でもよい）が、**必ず何かある**。

**後の決定**: [ADR-0005](../adr/0005-with-provision-and-head-blocks.md) は使用地点の
マーカーを採らず、通常の字句的シャドーイングでローカルとの衝突を解く。提供地点には
`with`を置く。この節は、その決定前に調査した材料として残す。

### 冗長さは頻度で配分できる

| 位置 | 頻度 | 許容できる冗長さ |
|---|---|---|
| 契約 (trait) | 契約ごとに1回 | 高 |
| スロット宣言 | スロットごとに1回 | 高 |
| 提供 | `main` と各 test。数箇所 | 中〜高（import で短縮可） |
| **使用** | 無数 | **ゼロ** |

→ 修飾は宣言と提供で払い、使用地点だけ短く保つ。全言語が import でやっていること。

### 副産物: マーカーは他の議論も畳む

使用地点にマーカーがあると:

1. `let db = ...` と衝突しない（衝突確率の問題が構造的に消える）
2. **使用地点で ambient が見える。**CONTEXT.md「書かせない、だが見える」の
   「見える」が IDE 頼みでなくなる。経由する関数は無記述のままなので売りは失わない
3. `.` が「値のように見せる」問題も、スロットが第二級かどうかの議論も要らなくなる
   （`@db` は明らかに普通の変数ではないので説明が不要）

## 6. 未修正のバグ

**スロット名とローカル束縛の解決先が、構文位置によって食い違う。**

```rhodolite
trait Database { fn save(self, u: Int -> unit) }
effect db: Database
struct Slot { n: Int }
impl Database for Slot { fn save(self, u: Int -> unit) { self.n = 1 } }
struct Local { n: Int }
impl Database for Local { fn save(self, u: Int -> unit) { self.n = 2 } }

fn handle(db: Local -> Int) {   // 引数名が偶然スロットと同じ
    db.save(0)                  // → スロットに行く
    db.n                        // → 引数に行く
}

fn main(-> Int) {
    let s = Slot { n = 0 }
    db(s): {
        let r = handle(Local { n = 7 })
        r * 10 + s.n
    }
}
```

`main -> 71` = `7 * 10 + 1`。警告もエラーも出ない。

原因: `eval.rs` の `Call(Field(..))` の腕で `slot_of` を見ているが、
`Field` の腕では見ていない。**綴りやマーカーの決定と無関係な defect** なので、
設計が決まる前に直してよい。直すときに上のプログラムを回帰テストにする。

**解決方針は決定、実装は未着手。**ADR-0005により、最も内側のローカル`db`が
両方の式で勝つ。`Local.save`が`db.n`を`2`へ変えるため、修正後の結果は`20`になる。

## 7. 未決の問いと、後に決まったもの

1. **解決済み: マーカーは入れない。**通常の`db.save(u)`と字句的シャドーイングを使う。
   ambient提供には`with`を置く（ADR-0005）
2. **強制するか、助言のままか。** = 「儀式をゼロにする言語」なのか
   「能力を握れない言語」なのか。ADR-0002 は「売り物は差し替え可能性」と書いており、
   これは人間工学の主張。助言なら CONTEXT.md の「誰が使っているか追えない →
   要求を推論して可視化」を**「スロットに置いたものは追える」**に直して実態に合わせる
3. **既定値をいつ評価するか**（§4）
4. **`effect` キーワードを改名するか。** 概念名は「スロット」で docs 全体に62回出る一方、
   キーワードだけ `effect` のまま。CONTEXT.md 自身がキーワードを「スロット」に翻訳して
   説明している。候補 `slot` / `ambient`。**2 が決まるまで保留**
   （宣言しているものが「置き場所」より「能力」に寄ると正しい名前が変わる）
5. **スロットは何個を想定するか。** CONTEXT.md は「差し替えたいものだけがスロット」と
   暗示するだけ。「十数個を想定し、1サービス1スロットのような使い方をすると
   名前空間が崩れる」という**破れる条件**を明文化する価値がある

## 9. 系譜表に足すべきもの

CONTEXT.md は Scala の `given`/`using` を挙げているが、**同じ形が UI 状態管理で
広く使われている**:

| Jotai | rhodolite |
|---|---|
| `atom(0)` をモジュールスコープで宣言 | `effect db: Database` をトップレベルで宣言 |
| `useAtom(countAtom)` — prop を経由させない | `db.save(u)` — 経由する関数は無記述 |
| `<Provider>` でサブツリーだけ差し替え | `db(x): { ... }` でブロックだけ差し替え |
| テストは Provider で包む | テストは提供ブロックで包む |
| 既定値を持つ | `= Postgres::new()`（§4） |
| 鍵は atom オブジェクトの同一性（文字列でない） | スロットは言語の一級の宣言物（文字列でない） |

推移性の経路が違うだけ（Jotai はコンポーネント木、rhodolite は呼び出しスタック）。
**大規模 React で回っているので、§5 の「干渉がひどそう」に対する実証データになる。**

差が残るところ:

| | Jotai | rhodolite |
|---|---|---|
| 提供忘れの検出 | 起きない（既定値必須） | コンパイルエラー + 到達経路 |
| 「この関数は何を要求するか」 | **分からない** | 推論して可視化 |
| 型射影 | 無い | `db::new()`（未実装） |
| 実行時コスト | ランタイムライブラリ | 単相化で消える（ADR-0003） |

`useAtom` を10階層下で呼んでいるコンポーネントが何を要求しているかは、
呼び出しグラフ全体を見ないと出ないので**ライブラリでは原理的に作れない**。
**言語でやる理由がここに残る。**
