# 診断の描画に `miette` を入れる

ADR-0004 改訂3 の申告制に従う。**依存を1つ足すのは構造の追加**なので、
足したこととその形をここに書く。

## 背景

実行前の診断は全部ただの `String` だった。`lex::Span` も AST の `span` も
既にあるのに、診断を組み立てる時点で捨てていた。README が売りに掲げる
「提供忘れを到達経路付きで報告」も、関数名の連なり
(`clock ← stamp ← promote ← main`)だけで、経路のどの呼び出しが原因かを
ソースで指せなかった。型検査の網が広がりきった時点で、次に品質を決めるのは
検査の数ではなく診断の見え方だった。

ソース抜粋・下線・行桁の描画は、書けば数百行になる。ADR-0004 の
Consequences には最初から「`miette`(到達経路付きエラー表示にそのまま使える)の
資産が効く」と書いてある。

## 決定

**`miette = { version = "7", features = ["fancy"] }` を1つだけ足す。**

依存はこれ1つに閉じる。`diag::Diag` は miette を知らない素の構造体のままにし、
`src/render.rs` の1ファイルでだけ `miette::Report` へ変換する。

`fancy` はカラー・罫線・折り返しのために推移依存を数個引き込む。抜粋付きで
描くことがこの依存を入れる目的そのものなので払う。依存量が問題になったら
`fancy` を外せば素のテキスト描画になる — 逃げ道は残っている。

長い行の折り返しだけは止めている(`wrap_lines(false)`)。到達経路の1行表現は
端末幅で折られると1行として読めなくなり、README もテストも1行を前提にしている。

## 却下した案

**自前で描く。** 行頭の探索・タブ幅・全角文字幅・複数行にまたがる span・
別ファイルの関連診断まで面倒を見ることになる。ここは言語の設計で語る部分ではない
(ADR-0004 の線引きで言えば「lexer や CLI を手書きしても語れる量は増えない」側)。

**診断ごとに variant を持つ `enum` を作り `#[derive(Diagnostic)]` する。**
エラーコードと構造化された help が最初から付くが、型検査だけで 42 種あり、
variant 定義とフィールドの受け渡しでこの change が数倍になる。位置を出すという
目的に対して過剰。`derive` は `thiserror` も要るので依存も1つ増える。
`Diagnostic` を手で実装すれば追加の依存なしで済む。
コードや `--explain` が要るときに `Diag` を分解して variant へ移せばよい。

## Consequences

- 依存木は空ではなくなった。`cargo build` に推移依存のコンパイルが乗る。
- `Diag` 側は miette を知らないので、外す・差し替える判断は `render.rs` の
  変換関数1つに閉じる。
- 到達経路はホップごとに `related` として描かれる。miette の複数ラベルは
  同一ソース前提なので、ADR-0006 のモジュール分割でファイルを跨ぐ経路は
  1つの枠には収まらない。`related` なら各ホップが自分のファイルを持てる。
