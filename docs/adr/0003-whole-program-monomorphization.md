# whole-program を維持し、エフェクト多相を単相化で消す

高階関数のエフェクトは渡された関数次第で決まる(`map` に Database を触る関数を渡せば
その `map` 呼び出しは Database を要求する)。型に正直に書くと
`fn map(xs: [A], f: (A -> B / e)) -> [B] / e` の **エフェクト変数 `e`** が現れる。
Koka が怖がられている原因はほぼこれ1つで、effect_design.md はこれを
「最大の技術的難所」と呼んでいた。

**rhodolite は `e` を型システムで解かない。whole-program 単相化で消す。**
高階関数を呼び出し地点ごとに複製し、エフェクトを実体で埋める。`e` は型に一度も現れない。
隠す工夫が要らない — 存在しないため。難所は「解決した」のではなく「非存在になった」。

## Considered Options

- **row polymorphism を実装する**(Koka/Flix と同じ道)。理論的に正しく、モジュール単独
  型検査もライブラリのバイナリ配布も可能になる。だが実装の山場が1つ増え、型に出る `e` を
  別途隠す工夫が要る。
- **高階関数のエフェクトを追わない**。実装は最軽量だが「提供忘れはコンパイルエラー」
  という売り(グローバル変数との差分)が穴あきになる。

## この判断が可能な理由

**「分割コンパイル」で欲しかったのはモジュール分割と増分ビルドだけ**であり、
モジュール単独型検査(他モジュールの本体を見ずに型・エフェクトが確定すること)は
要らないと判断した。前者2つは whole-program と両立する。

## 競合との位置関係

rhodolite が主張する性質は3つ — 推移する / 静的に検査される / 型に出ない。

| | 推移 | 静的検査 | 型に出ない |
|---|---|---|---|
| dynamic scoping, Odin/Jai context, OCaml 5 effects, React Context | ✓ | ✗ | ✓ |
| Koka, Unison, Flix, Effekt | ✓ | ✓ | ✗ |
| Haskell mtl / ImplicitParams, Scala ZIO の `R` | ✓ | ✓ | ✗ |
| Scala `given/using`, Kotlin context parameters | ✗ | ✓ | ✗ |
| **rhodolite** | ✓ | ✓ | ✓ |

3列とも埋まる行は他にない。ただし**道具は全部既製品**であり、次の3点は正直に扱うこと:

1. **単相化でエフェクト変数を消す機構は Flix が既に実装している**(effect-aware な
   specialization)。発明ではない。差は目的で、Flix は型に出すことを設計目標にしており、
   rhodolite は消すことを目標にしている — 同じ機構の逆向きの利用。
2. **「エフェクト=DI」という言い方は既にある**(Ruby の dry-effects / affect、
   Haskell の free monads vs DI の議論)。言語の一点突破に据えた例は見当たらないが、
   「誰も思いついていない」は誤り。
3. 第二級ブロックの発想は Effekt が近い。

**空席の理由は、誰も思いつかなかったからではなく代償が高いから。** 型に出さないためには
whole-program 単相化が要り、それはモジュール単独型検査の放棄を意味する。汎用言語として
配布される処理系はその代償を払えない。rhodolite は払える立場にいる — これが唯一の優位。

## ビルド時間について

whole-program = 遅い、は成り立たない。Rust/C++ のビルドが遅い主因は巨大な重複 IR の
最適化であり、Rust は**分割コンパイルしているからこそ**同じジェネリックを crate ごとに
単相化し直している。whole-program なら実体は1個で済み、単相化の総量はむしろ減る。
Moonbit と Roc が存在証明。関数単位で内容ハッシュを取れば増分ビルドとも両立する。

唯一の実リスクは、要求推論が呼び出しグラフの不動点であること(葉に1つ足すと上流の
要求集合が変わる)。ただし要求集合はキャッシュでき、**再計算結果がキャッシュと一致した
時点で伝播が止まる**ため、全再計算にはならない。rustc の red-green / salsa と同じ原理。

## 中核のアルゴリズム

要求集合は「自分の `Trait::` 呼び出し ∪ 呼ぶ相手の要求集合」で、依存は呼ばれる側にしか
向かわない。よって不動点反復は不要:

1. Tarjan で呼び出しグラフを強連結成分に縮約(相互再帰は1塊。同じ SCC 内の関数は
   不動点で必ず同じ要求集合になる)
2. 縮約後の DAG を逆位相順に1パス

到達経路は、要求集合の各要素に「どの呼び出し辺から入ってきたか」を1本添えるだけで
再構成できる(`Clock ← stamp ← promote ← handle`)。別途グラフを持つ必要はない。
v1 完了線の3項目(差し替え・可視化・経路エラー)は全部この1パスの副産物。
