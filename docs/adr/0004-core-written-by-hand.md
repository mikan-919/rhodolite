# 中核は手で書く

前作 iris は生成AIを使って開発され、mikan は「設計者としても実装者としても中途半端」
になったと総括している(志願理由書の素材)。Rhodolite の成功条件は
**進学ポートフォリオで語れること**と**自分でなるべく作ること**であり、
後者はこの総括への直接の回答として置かれている。

したがって AI との分担を規則として固定する:

| | 担当 |
|---|---|
| エフェクト推論 / ハンドラ解決 / 到達経路付きエラー生成 | **mikan が手書き** |
| lexer / parser / CLI / テストの定型 | AI 可 |
| 設計相談 / レビュー / 調査 | AI |

手書きの範囲は v1 完了線の3項目と一致させてある。面接で問われるのは「なぜその設計に
したか」であり、中核を手で書いていない設計は説明が浅いことが露見しやすい。逆に
lexer や CLI を手書きしても語れる量は増えない。**語る部分と手を動かす部分を一致させる**
のがこの線引きの意図。

## 改訂(同日): 要求推論の手順4〜6は AI が実装する

手順1〜3(スロット表・直接使用・呼び出し辺)を mikan が手書きした時点で、
残りの手順4〜6は「再帰と所有権を先に勉強する必要がある」段になった。
**mikan の判断で、手順4〜6は AI が書き、mikan がそれを写経する。**

この線引きが守りたかったのは手を動かすこと自体ではなく、
**面接で自分の言葉で説明できること**。写経は「読む」より深く、「自力で書く」より浅い。
1行ずつ手で打つ以上、意味の分からない行はそこで止まる — それが目的。
ただし線を黙って動かすと iris の再演になるため、動かしたことをここに記録する。

**残る規則**: 説明できない行は写経しない。止まったら分かるまで質問する。
手を動かす対象は AI 側に移っても、説明責任は mikan 側に残る。

**AI 側の制約**: 写経される前提でコードを書く。凝ったイテレータ連鎖や
省略記法より、長くても読み下せる形を選ぶ。「短いが打っても分からない」より
「長いが打てば分かる」を優先する。

手書きした範囲(手順1〜3)はそのまま残す。削除も書き換えもしない。

## 改訂2 (2026-07-26): 写経しなかった。手順1〜3の手書き実装も削除した

上の改訂で決めた「AI が書き、mikan がそれを写経する」は**実行されなかった**。
手順4〜6 は代筆されたものをそのまま採用している。線を黙って動かさないための
ADR なので、動かなかった事実もここに書く。

同時に、上の「手書きした範囲(手順1〜3)はそのまま残す。削除も書き換えもしない」も
破った。手順2・3 の `direct_uses` / `calls` と、それが使う `walk` / `walk_head` を
削除し、手順4 の `scan` に一本化した(コミット `ca098ac`、851 → 710行)。

理由は感傷ではなく食い違いのリスク。手順4 で `provided` を持ち回る必要が出た時点で
`scan` が手順2・3 と同じ仕事をしており、**同じ判定が2箇所にある**状態だった。
片方だけ直せば静かに食い違う。検査(手順2・3のテスト)は `scan_body` の
`escaping` / `calls` を見る形へ移してあり、確かめている性質は1つも減っていない。

「手書きを残す」は、それ自体が目的ではなく説明できることの手段だった。
手を動かした事実は git 履歴(`0efb4b8`, `b30b145`)に残る。動かない重複コードを
記念碑として置いておくことは、説明能力に何も足さない。

**未決**: 写経が実行されなかった以上、「面接で自分の言葉で説明できる」を
何が担保するのかが空いている。候補は、代筆されたコードを読んだあとに
**なぜその形かを自分の言葉で1〜3行書く**こと(例: なぜ `provided` を構造体に
持たず引数で下へ渡すのか / なぜ `Head::Ambient` の binder を `provided` を
増やす前に走らせるのか / なぜ不動点反復が止まるのか)。写経と違い、
**書けなかった時点で分かっていないことが露見する** — つまり検査になる。
採用するかは未決。決めたらここに改訂3として書く。

## Consequences

- 実装言語は Rust。iris と同じで、`nom`(パーサ)と `miette`(到達経路付きエラー表示に
  そのまま使える)の資産が効く。ただし mikan の Rust 経験は薄いため、これは
  「言語実装」と「Rust 習得」の二重課題であることを織り込む。
- v1 の機能の底は `examples/canonical.rd` が動く分だけとし、1つも先回りしない。
  中核を手書きする以上、スコープの膨張がそのまま完走リスクになる。
- まずインタプリタで作る。エフェクト推論とハンドラ解決の検証にコード生成は要らない。
  バックエンド(C出力 / LLVM / Cranelift / unsafe Rust出力)は最も高価で不可逆な決定
  なので、実際に必要になるまで決めない。
