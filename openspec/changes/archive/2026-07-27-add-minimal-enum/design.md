## Context

Rhodolite の正典は `rank: Rank` と書きながら、`Rank` 自体を宣言せず、
`struct Bronze {}` / `struct Gold {}` を値の名札として使っている。現在の AST、
モジュール解決、shape checker、評価器はいずれも struct を前提にこの代用を支えている。

この変更は enum を汎用的に完成させるものではない。正典の `Rank` を言語上の型として
表現し、後続の型検査が「`Gold` の型は `Rank`」という事実を利用できる最小の縦切りである。
ADR-0004 に従い、追加する構造と不変条件を実装前にここで申告する。

## Goals / Non-Goals

**Goals:**

- データを持たない enum と、その有限個の variant を宣言できる。
- variant を通常の裸の値として名前解決し、評価・等値比較できる。
- variant の所属 enum を静的に保持し、明らかな enum 型不一致を実行前に診断できる。
- 正典の `Bronze` / `Gold` 代用 struct を `Rank` enum へ置き換える。
- モジュール分割と字句シャドーイングに既存規則をそのまま適用する。

**Non-Goals:**

- データ付き variant、`match`、網羅性検査、enum のメソッド。
- `Rank::Gold` 形式の限定参照。
- すべての式に型を付ける完全な型推論。
- primitive、optional、配列、関数引数・戻り値の一般的な型検査。
- ADR-0003 の単相化。

## Decisions

### 1. enum は `Item::Enum`、variant は宣言名として表現する

AST に `Item::Enum { name, variants, span }` を追加する。構文は既存の改行区切り宣言に
合わせ、次の形だけを受ける。

```rhodolite
enum Rank {
    Bronze
    Gold
}
```

variant に payload や明示的な値を持たせる構造は作らない。重複 variant は意味検査で
決定的に報告する。

代替として既存のゼロフィールド struct へ enum 名だけを添える案は、struct の形と
「有限集合の一員」という異なる不変条件を同じ構造に残すため採らない。

### 2. variant は既存の宣言名前空間へ裸の名前で公開する

`Gold` は enum 本体の外でも裸の値として参照できる。モジュール解決は enum 名と各
variant 名を通常の宣言と同じ表へ登録し、variant を `module::Gold` という正準名へ
解決する。variant と struct・関数・effect などの同名宣言は、既存の宣言衝突として
拒否する。別モジュールの variant は既存の member import で個別に導入できる。

variant の所属は `variant の正準名 -> enum の正準名` の表で保持する。ローカル変数が
同名なら既存規則どおりローカルが勝ち、variant 参照にはならない。

代替の `Rank::Gold` は衝突を避けられるが、正典で合意した `Gold` という値の形を変え、
型パスと値パスの新しい解決規則も必要になるため、この最小変更では採らない。

### 3. 実行値に enum 専用表現を追加する

`Value` に enum 名と variant 名を持つ不変な値を追加する。評価器は未シャドーの正準
variant 名をこの値へ変換する。同じ enum の同じ variant だけが等しく、異なる
variant または異なる enum は等しくない。

struct 値を流用しないことで、フィールドアクセス・メソッド解決・表示が enum と
struct を取り違えない不変条件を作る。

### 4. 型検査は「分かる enum 型」だけを照合する

`typecheck` の宣言索引に enum と variant の所属を加える。また、ローカル束縛を
「名前の集合」から「分かっている場合だけ型名を持つ表」へ深める。型が分かる入口は
今回に限り、型注釈付き引数、struct リテラル、enum variant、およびそれらを直接束縛・
参照する式とする。

非 optional の enum 型が期待される次の位置で、右辺も enum variant と判明した場合に
所属を比較する。

- struct リテラルのフィールド値
- レシーバの struct 型が分かるフィールド代入

異なる enum なら診断する。同じ enum なら通す。右辺の型またはレシーバ型がまだ
分からない場合は、この変更では診断しない。これは完全な型安全性ではなく、
`Gold: Rank` という最初の型事実を検査器へ通す縦切りである。

代替として全式の型推論を同時に入れる案は、primitive・optional・配列・関数呼び出しの
規則を一度に決める必要があり、正典に必要な範囲を越えるため採らない。

### 5. 検査成功後の不変条件を限定する

この変更後、ロード・検査済みプログラムでは、全 variant 参照が一意な enum variant
宣言へ解決される。また検査器が両辺を enum と判定できた struct 生成・フィールド代入に
異なる enum の値は残らない。

未知型の式、optional、配列や呼び出し結果について同じ保証はまだしない。

## 足した構造と、なぜその形か (ADR-0004 改訂3)

| 構造 | なぜその形か |
|---|---|
| `Item::Enum { name, variants, span }` | variant を `Vec<String>` にしたのは、payload も明示値も持たせない決定を**型で言い切る**ため。フィールドを足せる形にすると「まだ足していないだけ」に読める |
| `Value::Enum { enum_name, variant }` | struct を流用すると「フィールド0個の struct」と区別が付かず、フィールドアクセスが黙って通ってしまう。別の変種にした瞬間、既存の `Value::Struct` を要求する腕が全部そのまま拒否になる |
| `Decls.variants` (variant → enum) | 所属を variant 側から1回で引ける向きにした。検査で欲しいのは常に「この値はどの enum か」であって、逆向きは要らない |
| `Locals` を名前の集合から `名前 → Option<型名>` へ | `None` を「まだ分からない」として持つことで、保証範囲の境界がデータ構造そのものに出る。分からない箇所で診断しないことが、書き忘れではなく型として見える |

**不変条件**

- variant の正準名から所属 enum の正準名を再構成できる(同じモジュールで宣言されるため)。
  所属を別の表で持ち回らなくても名前だけで辿れる。
- 検査を通ったプログラムでは、型が分かる位置に置かれた enum 値は宣言された enum に一致する。
  「型が分かる」の定義は決定4の4つの入口に閉じている。

## Risks / Trade-offs

- [裸の variant 名が宣言名前空間を消費する] → 既存の衝突診断と member import を再利用し、
  将来限定名が必要になった時点で別変更として設計する。
- [部分的な型検査が完全に見える] → 保証する位置と「型が分かる場合だけ」という境界を
  診断テスト、モジュールドキュメント、overview に明記する。
- [ローカル表の深まりが既存の shadowing を壊す] → 現在の引数・`let`・`for`・`self`・
  Head の全 shadowing テストを維持し、enum と同名のローカルを追加で固定する。
- [enum 値追加で評価器の match 漏れが起きる] → `Value` を網羅的に match する既存箇所を
  コンパイラで洗い出し、表示・等値比較・不正なフィールドアクセスをテストする。

## Migration Plan

1. enum の構文・AST・名前解決を追加し、既存プログラムが変わらずロードできることを確認する。
2. 型検査の variant 索引と限定的な照合を追加する。
3. enum 実行値と比較を追加し、正典を `enum Rank` へ移行する。
4. 全テスト、正典、CLI 診断、OpenSpec validate を実行する。

実装途中で互換性問題が出た場合は正典の代用 struct を残したまま enum 利用箇所を外せば
旧動作へ戻せる。外部データや依存関係の移行はない。

## Open Questions

なし。限定名、データ付き variant、完全な型検査は意図的に後続変更へ分離した。
