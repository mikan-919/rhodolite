## Context

配列リテラルと `for` は AST と評価器に既に存在するが、型注釈は名前と後置 `?` しか表せず、型検査器は配列式とループ変数を「分からない」に落としている。正典ではこの穴を未宣言の `Users` という名前で迂回しているため、`self.users` を反復したときの `u.id` を静的に検査できない。

この change は既存の「分かる型だけを照合し、後から逆向きに推論しない」という方針を保ちながら、配列から直接得られる型情報だけを既存の検査へ流す。

## Goals / Non-Goals

**Goals:**

- `[T]` を既存の型注釈位置で使えるようにする
- 配列リテラルを要素型付きで推論または期待型と照合する
- `for` の反復対象を検査し、ループ変数へ要素型を渡す
- 配列型を既存の field、引数、戻り値、代入、optional の型境界へ接続する
- 正典の `Users` を `[User]` に置き換え、ループ本体の既存検査を有効にする

**Non-Goals:**

- メソッド・関連関数の候補解決と呼び出し型検査
- trait 宣言と impl の署名・完全性の照合
- 型変数、ジェネリクス、配列の共変性
- 配列の所有権、借用、可変性、長さを型に含めること
- 空配列の型を後続の代入から逆向きに推論すること

## Decisions

### 1. 型は再帰的な形と、外側の optional 性を分けて持つ

AST と型検査器の型表現を、概念的に `Type { kind: Named(name) | Array(element), optional }` とする。これにより `[User]?` は optional な配列、`[User?]` は optional な要素を持つ配列として区別でき、`[[User]]` も同じ規則で表せる。

文字列名に `[T]` を埋め込む案は、モジュール名解決と optional の階層が曖昧になるため採らない。配列専用の非再帰フィールドを足す案も、配列の入れ子を特例化するため採らない。

### 2. 型構文は `[T]`、optional は完成した型への後置 `?`

既存の配列リテラルと同じ角括弧を型位置でも使う。式位置と型位置はパーサの入口が分かれているため曖昧性はない。後置 `?` は従来どおり直前の完成した型に付くので、`[T]?` と `[T?]` は異なる。

`Array<T>` のような名前形式は、言語にまだジェネリック型適用が無く、今回だけ擬似的に導入することになるため採らない。`T[]` は既存の後置 `?` と後置構文が競合し、入れ子が読みづらいため採らない。

### 3. 配列リテラルは期待型があれば文脈的に、なければ要素から型付けする

期待型が `[T]` の位置では、各要素を既存の適合規則で `T` と照合する。これにより `nil` や非 optional 値から optional 要素への注入も、struct field や関数引数と同じ規則になる。空配列 `[]` はこの経路で任意の期待配列型に適合する。

期待型が無い空でない配列は、推論できた全要素が同一型ならその配列型を得る。複数の既知要素型が異なれば診断する。型が不明な要素や `nil` しかない場合は、既存の裸の `let x = nil` と同様に配列全体も不明のままにし、後の代入から遡らない。

最初の要素だけを代表にする案は後続要素の誤りを見逃すため採らない。空配列へ専用の bottom 型を与える案は、現在の nominal な型集合へ新しい型関係を持ち込むため採らない。

### 4. 配列値の適合は不変、リテラル要素だけ期待型で検査する

既に `[T]` と分かっている値は同じ `[T]` にだけ適合し、`[T]` から `[T?]` のような要素型の昇格は行わない。配列が参照として評価され、将来変更されうる現状では、要素型の共変性を入れると書き込み時の安全性が崩れるためである。

一方、配列リテラルを期待型の位置に直接書いた場合は、生成時の各要素を期待要素型へ照合する。これは配列型の共変性ではなく、struct リテラルの field 値と同じ初期化境界として扱う。

### 5. `for` は非 optional 配列だけを受け取り、要素型を字句スコープへ入れる

反復対象の型が `[T]` と分かれば、ループ本体のローカル表へ `x: T` を入れる。既知の非配列型または optional な配列なら診断する。型が不明なら従来どおりループ変数も不明とし、追加診断は出さない。

optional 配列の暗黙展開は、通常 field access が optional receiver を暗黙展開しない既存方針と揃えるため採らない。

### 6. モジュール解決は配列の葉にある名前だけを正準化する

型名解決は型木を再帰し、`[User?]` の `User` だけを現在と同じ規則で正準名へ変換する。角括弧や optional 性は名前解決の対象にしない。

## Risks / Trade-offs

- [型表現の変更が parser、module、typecheck を横断する] → 型木の走査を小さな helper に集約し、既存の named type テストを維持する
- [期待型あり・なしで配列リテラルの結果が異なる] → `nil` と空配列を含む境界ケースを spec と単体テストで固定する
- [不明な要素を含む配列では検査が残る] → 今回は既存の段階的な保証に合わせ、メソッド解決後に不明集合をさらに狭める
- [正典の型注釈変更が評価動作へ影響する可能性] → 型注釈は実行時表現を変えず、正典の main と test の既存テストで回帰確認する
