## Context

モジュール解決後の `Program` では宣言名と参照名が正準名へ解決されている一方、`Item::Struct` の `fields` は評価器から参照されていない。`Interp` は struct 名の集合だけを持ち、`StructLit` に書かれたフィールドをそのまま実体へ入れるため、宣言と異なる形の値を生成できる。

この変更は `docs/overview.md` が次の穴として挙げる型検査の最初の縦切りである。ADR-0004 に従い、追加する構造と不変条件を実装前にここで申告する。

## Goals / Non-Goals

**Goals:**

- モジュール解決済みプログラム全体で struct 宣言と生成のフィールド集合を照合する。
- 既存の評価器へ不正な形の struct 値を到達させない。
- 後続の式型検査を同じ意味解析段階へ拡張できる、小さな境界を作る。
- モジュールを跨ぐ正準名と字句シャドーイングを既存規則どおり扱う。

**Non-Goals:**

- フィールド値と宣言型の一致を検査する。
- フィールドアクセスや代入のレシーバ型を推論する。
- 関数・メソッドの引数、戻り値、演算、optional、配列を型検査する。
- メソッド呼び出し辺の候補を型で絞る。
- ADR-0003 の単相化を実装する。
- span 付き診断や `miette` を導入する。

## Decisions

### 1. `typecheck` をモジュール解決と要求解析の間の独立段階にする

新しい `src/typecheck.rs` は `check(&Program) -> Vec<String>` を公開し、`main` は `module::load` の成功後、`requirement::analyze` より前にこれを呼ぶ。エラーが一つでもあれば既存診断と同様に全件表示して失敗終了する。

これは ADR-0004 上の新しい構造である。名前解決、ambient 要求解析、実行のどれにも struct の整形式検査を混ぜず、「実行前に AST の意味的不変条件を作る段」を一箇所に置くためである。将来の型検査もこの境界を深くする。

代替として評価時に検査する案は、呼ばれない関数の誤りを見逃し、型検査の足場にならないため採らない。`module` に入れる案は名前の解決と宣言種別の意味検査を混ぜるため採らない。

### 2. 永続的な型モデルはまだ作らず、宣言からローカル索引を組み立てる

検査は第1パスで正準 struct 名から宣言フィールド名への索引を `BTreeMap` / `BTreeSet` のローカル値として作り、第2パスで全ての関数・impl メソッド・test 本体を歩く。フィールド型は今回の判定に使わないため、新しい `Type` 列挙、型環境、推論結果、AST 注釈は追加しない。

順序付きコレクションを使うのは、不足・余分・重複フィールドの診断順をソースや hash seed に左右されない形にするためである。

代替として最初から完全な型表現と推論環境を作る案は、今回必要なフィールド集合の比較を越えて optional・配列・関数型の判断を先取りするため採らない。

### 3. 式走査は字句束縛を枝ごとに複製する

裸の `Ident` が struct 値かローカル値かを区別するため、走査は現在有効なローカル名を持つ。関数引数とメソッドの `self` から始め、`let` は右辺を先に検査して以降へ束縛を追加し、`for` と Head 本体は複製した集合へ束縛を追加する。ブロックから戻ると内側の束縛は消える。

これは `requirement::scan` と同じ字句スコープの不変条件を、異なる意味解析のために再実装する。汎用 walker を先に抽象化すると両解析が必要とする状態遷移の差を隠すため、共通化は実際の重複が安定してから判断する。

### 4. 検査成功後の不変条件を限定する

`check` がエラーなしで終わった `Program` では、全 `StructLit` が宣言済み struct を指し、宣言フィールドを過不足なく一度ずつ持つ。また、ローカルに隠されていない bare struct 値はフィールド0個である。

これは ADR-0004 上の新しい不変条件である。評価器はこの形を前提に実行できるが、フィールド値の型や動的なフィールドアクセスの正しさまでは保証しない、と境界を明示する。

## Risks / Trade-offs

- [要求解析と typecheck に似た AST 走査が二つ存在する] → 状態遷移が異なる間は別々に保ち、式形の追加時には双方の網羅性をコンパイラとテストで確認する。
- [「型検査」という名前に対して保証範囲が狭い] → capability を `struct-shape-checking` と呼び、Non-Goals と診断テストで境界を固定する。
- [span が診断へ出ない] → 既存の文字列診断に合わせ、span 対応は overview の後続項目として残す。
- [正準名がユーザー向け診断に現れる可能性がある] → 今回は既存のモジュール・要求診断に合わせる。表示名の改善は意味検査と分離する。

## Migration Plan

1. `typecheck` の単体テストで宣言、生成、bare struct、スコープ、モジュール正準名を固定する。
2. CLI パイプラインへ検査を挿入し、不正なプログラムが評価されない結合テストを追加する。
3. 全既存テストと正典プログラムを実行し、既存の有効な struct 生成が通ることを確認する。
4. 互換性問題が判明した場合は `main` から新段階を外せば旧動作へ戻せる。データ移行や外部依存の rollback は不要。

## Open Questions

なし。フィールド値の型検査と span 診断は意図的に後続変更へ分離した。
