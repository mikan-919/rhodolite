## Context

See `proposal.md` for motivation. MAP-Q6 (ROADMAP.md Decisions) already
fixed this task's observable contract; this document fixes how the four
already-existing passes (parser, `src/typecheck.rs`, `src/ownership.rs`,
generic instantiation/ambient inference) and the two backends
(`src/eval.rs`, `src/wasm.rs`/`src/wasm_data.rs`/`src/wasm_runtime.rs`)
each pick up `Push<T>` with the least new machinery.

Two facts, verified against the current tree before writing this design,
drive every decision below:

1. **No existing mechanism lets a declared trait `impl` have a
   compiler-supplied body.** `array_clone`/`array_drop`
   (`src/wasm_data.rs:849,868`) are structural, per-*layout* Wasm glue
   functions generated by `helpers_for` (`src/wasm_data.rs:440-491`) and
   invoked only by the ownership-plan-driven cleanup/move machinery — never
   reached through `xs.clone()`-style call resolution. The interpreter's
   equivalent (`Store::drop_value`/`clone_value`, `src/eval.rs:171,192`) is
   a single generic Rust function recursing on `StoredValue`, not a
   dispatched trait method either. The closest thing to "a call resolves to
   compiler-known behavior instead of a checked body" is `typecheck.rs`'s
   `.clone()` bypass (`fn declares_clone`/`fn clone_of`, lines 4179, 4190,
   intercepted in `resolve()` before trait-impl lookup at lines 3961-3967)
   — but that produces a dedicated `hir::ExprKind::Clone` node, not a trait
   dispatch, specifically because "there is no real `Clone` trait yet"
   (its own comment, decision 4 of an earlier change). MAP-075 is the first
   task that needs a *real* declared trait, with a *real* `impl<T> ... for
   [T]` participating in ordinary generic-impl method resolution
   (`Decls.traits`/`Decls.impls`, `struct Decls` typecheck.rs:70-91;
   `GenericOwner::Impl`, hir.rs:278), whose body is nonetheless not parsed
   Rhodolite source. (This turned out not to be reachable as planned — see
   Decision 1's deviation note: `Decls`/`GenericOwner::Impl` are struct-only
   throughout the current tree, so the implementation intercepts `.push` in
   `resolve()` instead, the same way the `.clone()` bypass above already
   does, rather than registering a real `impl<T> Push<T> for [T]`.)
2. **`&mut` is never auto-inserted for a bound mutable receiver.**
   `conform()` (typecheck.rs:3684) only auto-inserts a *shared* borrow;
   `conform_receiver` (typecheck.rs:4218-4240) requires the receiver's
   already-checked type to already be `&mut T`, else it reports "`&mut` を
   付けて排他借用を渡してください" (line ~3745). The apparent "implicit"
   `db.save(...)` call (no `&mut` at the call site, `examples/canonical.rd
   :52`, `docs/grammar.md:472`) is not auto-borrow at all — `db` is an
   *ambient slot*, resolved through a wholly separate path (`slot_target`,
   typecheck.rs:4244; the provider-mode check in `ownership.rs:1651-1723`)
   that never asks for a call-site modifier because the slot's mode is
   fixed once by its `with db(&mut db) { ... }` provider, not per call.
   `docs/grammar.md:490`'s `&mut pg.save(move u)` — the same `&mut self`
   method, called on a *bound local* `pg` instead of the slot `db` —
   confirms the modifier is required for the bound-local case. MAP-Q6's own
   wording ("db.save(...)と同じ", not "user.rename(...)と同じ") deliberately
   points at the slot precedent, not the bound-local one: `xs.push(y)` is
   meant to skip the modifier the same way `db.save(...)` already does,
   even though `xs` is a bound local, not a slot.

## Goals / Non-Goals

**Goals:**
- Add `Push<T>`/`impl<T> Push<T> for [T]` as a real, generically-resolved
  trait impl whose body is compiler-supplied, with the least new dispatch
  machinery — reusing generic-impl resolution, requirement inference, and
  ownership planning exactly as they already run for a parsed generic impl.
- Make `xs.push(y)` the one named, narrowly-scoped exception to the
  bound-mutable-receiver modifier rule, and make that exception impossible
  to trigger for any other method (parsed or builtin).
- Implement capacity-doubling growth and the OOM-traps-via-`unreachable`
  contract in Core Wasm by reusing existing pieces: the allocator's
  `alloc`/`extend` (`src/wasm_runtime.rs:271,438`, already traps on
  `memory.grow` failure) and `array_clone`'s alloc-and-copy shape
  (`src/wasm_data.rs:868-899`) for the realloc-and-copy path.
- Keep the interpreter's `push` a direct `Vec::push` on the already-`Vec`-
  backed `StoredValue::Array` (`src/eval.rs`), with no capacity concept of
  its own (Rust's `Vec` already amortizes growth; MAP-075's capacity-
  doubling *contract* is a Wasm-backend-visible guarantee only, not
  something the interpreter needs to replicate byte-for-byte since nothing
  observes Rust's `Vec` growth factor from Rhodolite source).

**Non-Goals:**
- `len()` or `xs[i]` (ROADMAP Future Directions) — `push`'s internal
  length/capacity bookkeeping stays unreadable from source.
- Any general auto-borrow rule change beyond the one named `Push<T>::push`
  exception — every other `&mut self`/consuming method, builtin or not,
  keeps requiring its call-site modifier.
- A general "compiler-builtin trait impl" framework for arbitrary future
  traits. This change adds exactly the registration `Push<T>` needs; a
  second builtin-bodied trait (if one is ever proposed) can decide then
  whether to reuse or generalize this shape.
- Any change to `array_clone`/`array_drop`, the allocator's block format,
  or the ABI v1 wire encoding.

## Decisions

### 1. `impl<T> Push<T> for [T]` is a dedicated HIR node (`ExprKind::Push`), not a `GenericOwner::Impl`

**Implementation deviation from the plan below, verified against the tree
before implementing:** `check_generic_impls` rejects any impl target that
is not a struct, and `instance_owner`/`TraitImplDecl::type_`/the
generic-impl index are all struct-typed throughout `typecheck.rs`. Routing
`impl<T> Push<T> for [T]` through `GenericOwner::Impl` as originally
planned would first require building the general "generic impl targeting
`[T]`" mechanism MAP-080 is scoped to add — a bigger, unrequested surface
this change's Non-Goals already exclude. The implementation instead follows
the `array_clone`/`array_drop`/`.clone()` precedent directly: `resolve()`
(`src/typecheck.rs`) intercepts a `.push` call on an array-typed receiver
before generic-impl lookup — the same interception point already used for
the builtin `.clone()` (`fn declares_clone`/`fn clone_of`) — and lowers it
straight to a new `hir::ExprKind::Push { array, value }` node (`push_of`,
`push_receiver`, `src/typecheck.rs`) instead of resolving to any
`CallTarget::Method`. `Push<T>` itself is still declarable as an ordinary
generic trait (`GenericOwner::Trait`, reusing MAP-025's machinery) so the
contract's trait-declarability requirement holds, but there is no `impl`
block, parsed or synthesized, backing `[T]`'s conformance — the array
receiver simply never reaches generic-impl resolution because the `.push`
interception fires first, the same way `.clone()` never reaches trait-impl
lookup either.

Every pass that already switches on `hir::ExprKind` gets one new arm
instead of one new callable-body-kind arm: `src/requirement.rs` and
`src/ambient_abi.rs` walk only the `array`/`value` subexpressions and
contribute no requirement or provision; `src/ownership.rs` treats the
receiver as an exclusive place-borrow and the value as `Need::Argument`
(move-once), the same shape a parsed `&mut self` call already produces;
`src/eval.rs` and `src/wasm.rs`/`src/wasm_data.rs` each get one new arm at
their expression-lowering entry point that runs/emits `push`'s behavior
directly. Generic instantiation/specialization keying (MAP-040) is
untouched — the builtin has no generic declaration of its own to
instantiate.

**Alternative considered:** synthesize a fake HIR body (e.g. hand-built
`hir::ExprKind` nodes that "happen" to implement push using only
already-legal HIR, the way a macro-expanded body would). Rejected — `push`
needs raw buffer manipulation (read/write `{data, len, capacity}`,
`memory.grow`-driven realloc) that has no representation in checked HIR at
all (the same reason ROADMAP calls this "生バッファ操作を要するため通常の
Rhodolite ソースでは書けない" for `array_clone`/`array_drop`); a fake body
would just be dead HIR the backend still special-cases separately, adding a
layer for no benefit.

**Alternative considered (originally planned, superseded by the deviation
above):** register the impl as a `GenericOwner::Impl` with a sentinel
builtin-body marker on `hir::Callable`, so every already-generic-impl-aware
pass (instantiation keying, ownership planning, ambient ABI planning) picks
it up through its existing struct-impl machinery with one new body-kind
arm each. Superseded — that path is blocked by the struct-only assumptions
described above, and unblocking it means building MAP-080's array-generic-impl
mechanism first, which is out of this change's scope.

### 2. The receiver-modifier exception is keyed to the same builtin interception as Decision 1, not to any syntactic pattern

Per Decision 1's actual mechanism, `push` never reaches `conform_receiver`
(typecheck.rs:4218) at all — the array-receiver `.push` interception in
`resolve()` fires first and calls a dedicated `push_receiver`
(`src/typecheck.rs`) instead. `push_receiver` treats the receiver the way
`conform()` already treats a `&self` receiver — auto-insert the exclusive
borrow when the receiver is a place, pass an existing `&mut [T]` through
unchanged, and reject a shared borrow or a temporary outright — instead of
requiring the caller's `&mut`. Every other call, including a user-declared
method named `push` on an unrelated type, and including any future
non-array `impl Push<T> for SomeType` if one is ever allowed, still goes
through the unmodified `conform_receiver`/`&mut`-required path, because the
interception in `resolve()` keys off "this call resolved as the builtin
array-receiver `.push`" (an array-typed, non-optional receiver — see
Decision 1) — the same way it keys off "array receiver" rather than off the
method name `"push"` or the trait name in isolation, so an unrelated
struct's `push` method is never touched.

**Alternative considered:** make the exception apply to *any* method whose
trait is `Push`, or generalize "compiler-builtin `&mut self` methods skip
the modifier" as a blanket rule for all builtin-bodied impls (decision 1).
Rejected — nothing in MAP-Q6 asks for a general rule, only for `xs.push(y)`
specifically; keying to name/trait instead of the exact resolved impl would
silently exempt a hypothetical future user-declared `Push` impl for another
type from the modifier requirement too, which is a bigger, unrequested
surface change and would need its own design/spec sign-off.

**Alternative considered:** route `xs.push(y)` through the ambient-slot
call path (`slot_target`) the way `db.save(...)` actually achieves its
modifier-free call, e.g. by treating every array value as an implicit
slot. Rejected outright — slots are declared once per program
(`effect name: Trait`) and resolved by name shadowing rules
(`requirement-map.md`'s `名前は隠す` note); an arbitrary local array is not
nameable that way, and forcing arrays through slot machinery would need
inventing a new "per-value slot" concept nothing else in the language has.
The design instead reuses only the *outcome* `db.save(...)` demonstrates
(no call-site modifier needed for a `&mut self` receiver) via the narrow,
explicit exception above — not the *mechanism* slots use to get there.

### 3. Capacity growth and realloc reuse `array_clone`'s alloc-and-copy shape; no new allocator primitive

`array_clone` (`src/wasm_data.rs:868-899`) already allocates a fresh
buffer sized for a known element count/stride and `MemoryCopy`s the
source's live elements into it — exactly the shape a `push`-triggered grow
needs, with two differences: the new capacity is computed (`0 -> 1`, else
`capacity * 2`) rather than copied from the source's own capacity, and the
old buffer is freed (via the existing `free`, `src/wasm_runtime.rs`'s
`ALLOC`/`FREE` convention, lines 60-62) after the copy instead of the
source staying live. `push`'s generated function: read `len`/`capacity`;
if `len < capacity`, write the new element at `element_address(data, len,
stride)` and increment `len`; else compute `new_capacity` (1 if `capacity
== 0`, else `capacity * 2`), `alloc` a buffer of `new_capacity * stride`,
`MemoryCopy` the `len * stride` live bytes over, `free` the old `data`
pointer (skipped when `data` is the reserved "empty/uninitialized" sentinel
address 0, ADR-0011 §1), store the new `data`/`capacity`, then write the
new element and increment `len` as above. OOM during `alloc`'s internal
`extend` already traps via `trap_if` on `memory.grow`'s `-1` result
(`src/wasm_runtime.rs:438-467`) — `push` calls the existing `alloc`
function by index and adds no new trap condition.

**Alternative considered:** grow capacity by a fixed increment or to
exactly `len + 1` each time (no doubling). Rejected — ROADMAP's completion
criteria fix doubling explicitly ("倍々成長"), and amortized doubling is
also what avoids `push` in a loop becoming quadratic, which the existing
allocator-reuse/no-leak test technique (`src/wasm.rs`'s capped-page,
bounded-loop tests, e.g. line ~4003) would otherwise need a much larger
page cap to tolerate.

### 4. Interpreter `push` is a direct `Vec::push`, with no interpreter-visible capacity contract

`StoredValue::Array` is already `Vec<OwnedValue>` (`src/eval.rs`). `push`
evaluates `y`, moves it in via ownership-checked argument evaluation (the
same move-once path any owned call argument already takes), and calls
`values.push(y)`. `Vec`'s own growth strategy is an implementation detail
Rust does not expose and Rhodolite source cannot observe (no `len()`,
`xs[i]`, or capacity introspection in scope) — differential parity
(design goal, and this change's new differential-execution scenarios) only
requires matching *array contents, length, and element ownership final
state* between interpreter and Wasm, never matching internal capacity
numbers between the two backends. The 0→1→2→4 doubling contract is
Wasm-codegen-visible only insofar as it is what the Wasm-side snapshot/unit
tests pin directly against `wasm_data`'s buffer fields.

**Alternative considered:** give the interpreter its own explicit
`capacity`-tracking wrapper around `Vec` to mirror the Wasm buffer's fields
one-for-one. Rejected as pure duplication — no requirement or scenario in
`array-push`'s spec needs the interpreter to expose or match a capacity
number, only the Wasm backend's own tests do, and `Vec::push` already
gives correct content/length/ownership behavior for free.

### 5. `push`'s differential fixture(s) are added inline in `src/differential.rs`, alongside pattern MAP-070 used for `GENERIC_*`

Following `compile-generic-instantiations-to-wasm`'s Decision 4 precedent:
short, single-purpose fixture sources belong inline as `&str` constants
registered in `FIXTURES`, not as new files under `tests/fixtures/`, when
they need only one or two small declarations. This change adds one fixture
exercising a capacity-growth boundary (enough pushes to cross at least one
capacity doubling) and one exercising a moved-in non-`Copy` element (e.g. a
small struct), sized similarly to the existing `GENERIC_*` fixtures.

**Alternative considered:** extend `tests/fixtures/wasm-owned-data/all-
constructs.rd` with `push` calls in place. Rejected — that fixture's
purpose is "every owned-data construct once, together"; folding in
capacity-boundary-specific pushes would blur what its own snapshot answers
for, the same reasoning MAP-070's Decision 4 used to keep its owned-value
generic fixture separate.

## Risks / Trade-offs

- [Intercepting `.push` in `resolve()` ahead of ordinary method/generic-impl
  lookup — the same shape as the existing `.clone()` builtin — is exactly
  the kind of "no branch for this came from a builtin" property earlier
  MAP-0xx designs deliberately avoided (see MAP-070 design.md Decision 1's
  citation of MAP-060's reasoning)] → Accepted narrowly: unlike those
  cases, MAP-Q6 explicitly requires call-site behavior to differ for
  `xs.push(y)` specifically, so *some* branch is unavoidable; Decision 1/2
  keep it to the smallest possible surface (one array-receiver-shaped
  interception, mirroring the precedent `.clone()` already set) rather than
  a name- or trait-keyed rule that would leak to hypothetical future impls.
- [A dedicated builtin-call HIR node (`ExprKind::Push`) is new machinery
  every later builtin-trait proposal will be tempted to reuse or diverge
  from] → Accepted; Non-Goals explicitly declines to generalize it now. If
  a second builtin-bodied trait is proposed later, that change can decide
  whether to reuse this shape (or the originally-planned
  generic-impl-with-builtin-body shape, once MAP-080 makes it reachable for
  non-struct targets) with a second real data point in hand.
- [Realloc-on-grow doubles peak memory during the copy (old + new buffer
  briefly live)] → Accepted; this is inherent to any copying grow strategy
  and matches what `array_clone` already does for an explicit `.clone()`;
  not a new class of cost this change introduces.

## Migration Plan

1. Add `Push<T>` trait declaration support (an ordinary `GenericOwner::Trait`)
   and the `resolve()`-level interception that lowers an array-receiver
   `.push` call straight to `hir::ExprKind::Push` (Decision 1); confirm it
   type-checks, is reachable with no user-written `impl`, and contributes
   no ambient requirement.
2. Add the `push_receiver` exclusive-borrow auto-insertion (Decision 2) and
   the ownership-planning move-once treatment of `push`'s second argument;
   add focused typecheck/ownership tests for both, including a negative
   test that an unrelated `push`-named method still requires its `&mut`
   modifier through the unmodified `conform_receiver` path.
3. Implement interpreter execution (Decision 4) and add eval-level
   scenario tests for content, length, and owned-element final state.
4. Implement Core Wasm codegen: the `push`-per-layout generated function
   (capacity read, append-or-grow, alloc/copy/free per Decision 3), wired
   the same way `array_clone`/`array_drop` are wired per reachable array
   layout. Add `src/wasm.rs`-local snapshot/unit tests for the 0→1→2→4
   growth sequence and a capped-page bounded-loop test proving repeated
   pushes reuse freed memory rather than leaking.
5. Add the two differential fixtures (Decision 5) and register them in
   `FIXTURES`; run the full differential suite.
6. Sync the `array-push` (new), `method-call-type-checking` (modified),
   and `differential-execution` (modified) delta specs.
7. Run the full test suite, `cargo fmt --check`, and Clippy with warnings
   as errors; confirm two consecutive builds of each new fixture are
   byte-identical (ROADMAP's MAP-010–MAP-100 common completion
   condition); commit the stable, passing state as a single snapshot.
8. Mark MAP-075 `done` in `ROADMAP.md`.
9. Rollback is a plain revert: this change adds one new trait/impl
   registration path, one narrowly-scoped call-site exception, and codegen
   for one new operation — no public ABI, existing data representation, or
   unrelated runtime contract changes.
